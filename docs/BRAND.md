# 擎天 AI：任务有执行、有证据、有交接

擎天是一套可直接启动的本地 AI 任务引擎：团队提供目标、授权仓库与验收环境；擎天组织职责和依赖，在独立 worktree 调用真实 Codex Worker，记录事件、失败与证据，结果返回看板和报告。

**对用户，不该每次中断都重新解释一遍。对执行，不该每次“继续”都重新开始或扩大授权。**

接入宿主协调能力后，擎天希望让用户把需求集中交给大管家：长工作由执行任务承担，进度与阻塞有归属，收尾有可以核对的证据。这里的大管家和执行者是智能体职责，不是拟人化员工；宿主能力、人工约定和公库实现必须分开介绍。

## 用户真正遇到的麻烦

| 用户处境 | 过去需要自己做 | 擎天的协作方式与条件 |
|---|---|---|
| 额度或限流中断 | 找出停在哪个会话，再解释已批准需求。 | 由大管家核实原因、授权与检查点，借助宿主续接确切任务。 |
| 长实现正在进行 | 等入口腾出手，或到处复制需求。 | 长工作交给执行任务，大管家派发后释放入口；依赖宿主协调接入。 |
| 代码交了，外部权限没到 | 猜测哪些能交、谁还欠动作。 | 分列本地成果、待接入事项及责任归属；不假称自动拆单。 |
| 执行者说完成 | 自己翻日志判断有没有测、测了哪个版本。 | 任务与 run 分开，按证据门核对，并明确缺哪份回执。 |
| 发布已暂停 | 担心“其他工作继续”顺带触发上线。 | 保留暂停限制，只续获准范围；外部流水线仍须接入方落实控制。 |

## 主打案例：用户只说一次“继续”

> 用户：“刚才没 token 了，现在可以了，继续。”

这是从一次**宿主辅助协调实践**提炼的全新通用样例，不是原截图或原业务案例的公开副本。它说明一种可落地的协作方法，不证明开源 CLI 无接入就能自动跨会话恢复。

1. 大管家先读原失败，确认是额度、短时限流还是环境问题，核实当前是否可继续。
2. 找到确切原任务与唯一 owner，读取检查点，保留已批准方案、已有修改和原权限。
3. 借助受支持的宿主工具发送续接说明，只让执行者补完剩余部分。
4. 告诉用户归属、交付与阻塞后释放入口，用户不必逐个去执行会话重复需求。
5. 执行者交新产物和实际检查回执，大管家核对证据再收尾。

可对外讲：“工作中断了，不必让用户重新当一次调度员。先把中断、授权和检查点核实清楚，再让原执行任务把剩下的事接着做。”

不可省略条件：额度仍耗尽且宿主不允许新执行时只能等待；任务不唯一或授权不完整时要澄清。这不是补额度、绕限流、自动充值或消费 reset，也不会暗中切便宜模型、无限重开会话，或恢复用户暂停的发布。

## 收益要落在可观察的变化上

- **少重复讲述。** 已批准方案与上下文通过检查点交接；无法可靠定位时才问必要问题。
- **少充当中转站。** 大管家给出执行归属与交付约定，详细日志留在执行任务，不把用户入口占成长轮询。
- **少猜下一步。** 本地交付、外部等待和缺失验收分别说明，写清谁需要做什么。
- **更稳妥地继续。** 保留文件归属、未提交成果和暂停限制，避免恢复动作改变用户意图。
- **更容易核对结果。** 报告绑定产物版本与原始回执，不以百分比、`item.completed` 或模型自述代替完成。

这些是协作目标和可检查的结果，不提供未经测量的效率百分比、节约费用或无人值守成功率承诺。

## 四个价值

- **任务不只存在于对话里。** task/run/session/event/evidence 分开持久存储。
- **分工不靠拟人承诺。** coordinator、frontend、backend、qa 表示职责路由；真实执行看 run 和证据。
- **执行与验收分开。** 退出码不等于通过，证据不足停在验收阶段。
- **知识人机共建。** Markdown/Obsidian 可读、索引可重建；Worker 按合同读引用，不把旧文档当新任务。
